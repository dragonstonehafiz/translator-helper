Backend and models

The backend is organized around HTTP routes, task execution and a shared manager for model clients.

Current implementation · 3 October 2026

Startup

The server.py lifespan starts three daemon threads: one for the LLM, one for audio, and one for search. Each calls the shared manager. Readiness can still be false while initialization runs.

Server lifespanStarts loading threads.
ModelManagerCreates a client if its slot is empty, then initializes it.
Client configurationProvider code reads saved settings.
Settings pageDisplays readiness and loading errors through utility endpoints.

Initialization failures are recorded in manager error fields. The server lifespan currently has no model-shutdown cleanup after its yield.

ModelManager responsibilities

A singleton means one shared instance within the backend process. The manager keeps one LLM slot, one audio slot and one Tavily slot. It currently constructs LLMDeepSeek, AudioWhisperX and SearchTavily. Other provider implementation files are available, but there is no active multi-provider registry.

ResponsibilityCurrent behavior
Instance ownershipCreates and returns clients through get_llm_client(), get_audio_client() and get_search_client().
LoadingCalls initialize(); tracks loading booleans and the latest loading error.
ReadinessChecks whether a client exists and reports status loaded.
SettingsForwards configure(settings) to clients.
ExecutionOffers llm_infer() and audio transcription wrappers; some task code also calls a retrieved client directly.
Output writingaudio_transcribe_file() also names and saves the generated subtitle file.

Removing ModelManager would require moving its lifecycle, readiness, settings and file-writing responsibilities to other components.

Model interfaces

LLMInterface combines inference with initialization, shutdown, configuration/schema methods, status, running state, device access, model access and temperature access. AudioModelInterface has a similar shape, with line/file transcription and available-device methods instead of inference and temperature.

Both contain a helper for finding configuration files in backend/files/config/. Provider implementations handle their actual settings persistence. Sharing configuration behavior is a possible future design choice; there is no common configuration interface today.

Source: backend/llm/interface.py and backend/audio/interface.py.

Model status

Loaded means initialization succeeded. Loading is a manager flag while initialization runs. Running can mean either an active orchestrator task or a client flag controlled by task code. These are separate pieces of state.

GET /utils/running uses the orchestrator's active task type and the LLM/audio task-type sets. It does not use the manager's is_llm_running() or is_audio_running() methods.

The settings load request includes a provider field, but the current load handlers use request.settings and do not select a provider from that field. See backend/routes/utils.py.

Tavily search

Tavily is a concrete search client in search/, owned by ModelManager. It does not implement the LLM or audio interface. TaskWebSearch retrieves it and calls search() directly to collect snippets for library proposals.

If no queries exist, the task skips searching. If queries exist and search is unavailable, it raises an error. Source: backend/orchestrator/library/task_web_search.py.

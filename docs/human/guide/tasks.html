Orchestrator and task chains

A workflow is the whole operation a user starts, such as translating a file. It runs an ordered list of tasks, each taking one typed input and returning one typed output.

Current implementation · 4 October 2026

Running a workflow

A route calls the workflow's start function in orchestrator/workflows/. That function loads the input once (subtitles are read into memory here), builds the typed input data and its task list, and hands them to TaskOrchestrator.run().

Workflow start functionLoad inputs, build typed data and the task list.
run()Reject if busy; otherwise record the workflow and return at once.
Each taskCheck input type, run, check output type, pass it on.
finish, then cleanupSave the output file or keep the result; always delete temp inputs.

The orchestrator runs one workflow at a time on its own background thread. run() either rejects the request without touching the running workflow, or accepts it and takes over: from then on it records progress and errors, and its cleanup deletes the uploaded temp files whether the run succeeds or fails. On server shutdown it waits for the running workflow to finish before the models are released.

Source: backend/orchestrator/task_orchestrator.py and backend/orchestrator/workflows/.

Task inputs and outputs

Every task declares its input and output as dataclasses in orchestrator/task_data/, one module per kind of workflow. Required fields have no defaults, so a missing value fails as soon as the next object is built, and the orchestrator checks each task's input and output type as the workflow runs. A step that adds fields builds the next type with extend(); a step that only changes fields uses replace().

Tasks don't save files, delete uploads or record their own status. They return data or raise; the workflow's finish callback saves output and the orchestrator records the result or error.

The six workflows

WorkflowTasks in orderResult
translate_lineTaskTranslateLineTranslated text
translate_fileTaskPrepareTranslationBatches → TaskSelectLibraryContext → TaskTranslateBatchesSaved file in translated/
review_fileTaskPrepareReviewBatches → TaskSelectLibraryContext → TaskReviewTranslatedBatches → TaskRetranslateReviewedLinesSaved file in reviewed/, plus the number of corrected lines
update_libraryTaskExtractLibraryFindings → TaskClassifyLibraryFindings → TaskGenerateSearchQueries → TaskWebSearch → TaskGenerateLibraryProposals → TaskDeduplicateCharacterUpdatesProposals
transcribe_clipTaskTranscribeClipTranscribed text
transcribe_fileTaskTranscribeFileSaved file in transcribed/

Review loads both files and checks that they have the same number of lines before any model call. The library update extracts names, terms and events, compares them with the library, searches the web for unknown names and terms (events are not searched), and proposes additions. The user accepts proposals through the library editing endpoints; the workflow never writes to the library itself.

Shared steps

Translation and review share their batch-planning code (translate_file/batch_preparation.py). Translation then splits any batch larger than the requested batch size, asking the model again and falling back to an even split if its reply is invalid. Review keeps the model's batches as planned.

Both workflows use the same TaskSelectLibraryContext. It is created with the data type it runs on and returns that same type, so review-only fields such as the translated subtitles pass through untouched. Without a series or with an empty library, it skips the model call.

Source: backend/orchestrator/translate_file/ and backend/orchestrator/review_file/.

Progress, errors and logs

The orchestrator keeps one state record per workflow in TaskStateHandler: status, active task, progress, message, ETA, result and error. Tasks only report progress through the report_progress callback they are given. Starting a workflow replaces its previous record; a failure keeps the task that failed and its last progress, so the UI can say where it stopped.

Each run gets its own log folder, files/logs/<workflow>/<timestamp>-<file name>/, kept after success or failure. Tasks write diagnostics there through the write_log callback, for example the model's batch plan and, separately, every batch the splitter repaired. See the polling rules for how the frontend reads the state.

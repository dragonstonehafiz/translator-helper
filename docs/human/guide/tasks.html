Orchestrator and task chains

A chain is an ordered list of task objects. Each task receives the previous task's returned dictionary.

Current implementation · 3 October 2026

Task execution

The routes decide which tasks belong in a chain. TaskOrchestrator stores that list, copies it when execution begins, and runs it sequentially. It tracks the active task type and writes start, finish and failure messages to the shared log.

Route runnerClear list, add tasks, supply initial_data.
set_data(output)Replace the next task's input dictionary.
run_task()Execute synchronously and return a dictionary.
Next taskReceive that return value as its entire input.

The runner rejects execution when it is already running and resets its active flags in finally. This is an in-process sequence, not a durable queue or dependency graph. Task-list assembly and starting execution are separate operations; the lock should not be read as a transactional submission API.

Source: backend/orchestrator/task_orchestrator.py.

Task inputs and outputs

BaseTask requires run_task(), but does not declare required input keys or validate the output dictionary. Tasks read keys themselves, often with data.get(...) defaults. Missing values can therefore fail later, or activate fallback behavior.

The runner does not merge old and new data. Intermediate tasks preserve upstream values using {**data, "new_key": value}. Returning only the new key would discard everything else needed downstream.

A task's return value feeds the next task. ResultHandler.set_complete(...) feeds the polling API. These are different outputs; writing one does not automatically write the other.

Library tasks extract candidates, compare them with the existing library, research them and prepare deduplicated proposals. The user accepts proposals through library editing endpoints; the chain does not directly save them as accepted entries.

Task reuse

TaskPlanTranslationReviewBatches inherits the translation batch planner, calls its implementation and forwards translated-file information. TaskSelectLibraryContextForReview inherits the translation context selector, changing its task type and log filename.

The review chain does not include TaskSplitOversizedBatches. Sharing the planner therefore does not mean both chains have identical batch processing.

These subclasses reuse task behavior, including progress/result reporting and singleton access. The reusable unit is currently an orchestrator task with side effects, rather than only a pure planning or context-selection function.

Source: backend/orchestrator/review_file/task_plan_translation_review_batches.py and backend/orchestrator/review_file/task_select_library_context_for_review.py.

Progress and error tracking

Tasks explicitly write to ResultHandler and ProgressHandler. Each store holds the latest entry per task type, protected by a lock. They do not hold a history of uniquely identified jobs.

A task typically marks itself processing, writes progress, then marks completion. On failure it records an error and raises. The orchestrator logs the exception and stops the chain; route-level wrappers record the error under the final type that the UI is polling.

The translation and review runners clear the final result before running. Polling can then report an intermediate task's progress until the final task has its own record. See the polling rules.

Refactoring considerations

These are design questions, not changes made by this draft:

  • Should each task declare and validate its inputs before execution?
  • Should shared batch/context logic be separate from task status and logging?
  • Should a chain submission own its task list instead of assembling a shared mutable list?
  • Should results identify a particular run rather than only a task class?
  • Should one layer own temporary-file cleanup for the whole chain?

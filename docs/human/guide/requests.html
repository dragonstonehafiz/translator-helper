Translation request flow

File submission, background processing, result polling and downloads.

First draftCurrent implementation · 3 October 2026

1. File submission

The Translate page gets its selected file and series from shared state, then calls ApiService.translateFile(). The service sends multipart form data to POST /translate/translate-file, including languages and batch size.

The route checks orchestrator availability and LLM readiness. It copies the upload into an operating-system temporary file and optionally loads the selected series. It schedules run_translation_file_chain through FastAPI BackgroundTasks.

The initial response has status processing and task type TaskTranslateFile. It does not contain the finished subtitles or a unique job ID.

2. Task execution

PlanAsk the LLM for semantic groups of subtitle lines.
SplitRepair groups larger than the requested batch size.
ContextSelect relevant library information if a series is available.
Translate and saveTranslate batches and save under sub-files/translated.

The route runner creates a timestamped log directory and supplies it to every task. Tasks can write numbered JSON diagnostics. The final translation task preserves the input extension in the output filename and lets the subtitle library save that format.

Source: backend/routes/translate.py and backend/orchestrator/translate_file/task_translate_file.py.

3. Result polling

The page repeatedly calls GET /task-results/TaskTranslateFile. build_task_response() reads the result store and the orchestrator:

ConditionResponse
No final record; orchestrator runningprocessing, with the currently active task's progress if available.
No final record; orchestrator idleidle.
Stored final record is processingprocessing with progress for that final type.
Stored final record is completecomplete with its result payload, which may be null.
Stored final record is errorerror with the stored message.

The frontend copies these updates into StateService. AppComponent reads that state to draw the global progress overlay. The overlay does not poll the backend itself.

Progress counts belong to the active stage. 1 of 1 during planning is not the same unit as 100 of 200 lines during translation. This is stage progress, not a weighted percentage for the entire chain.

Source: backend/routes/shared.py.

4. Completion and downloads

File translation marks completion without a result payload. The page refreshes the file list for sub-files/translated. Downloading is a separate request through ApiService.getFileBlob().

Other operations have different results: line tasks return text; library updates return proposals; review returns a result payload and also writes a corrected file. File downloads require a separate request.

Error handling

JSON responses use {status, message, data}. Some route rejections return an error envelope with the normal HTTP response status; validation and unhandled exceptions also have HTTP error responses. Frontend code therefore needs to inspect both the envelope and transport failures.

A background exception happens after the start response. The chain runner records it under the final task type so a later poll can report it. In-memory error records disappear when the backend restarts; diagnostic files can remain.

Sources: backend/utils/api_response.py and frontend/src/app/services/api.service.ts.

Requests outside the orchestrator

Listing files, downloading files, loading series and editing library entries use direct request/response handlers. Model loading uses utility endpoints and a threadpool rather than the task orchestrator. The task polling protocol is specifically for transcription, translation, review and library-update work.
